1. The Bitemporal Datom Model
A classic Datomic datom is a 5-tuple: (Entity, Attribute, Value, Transaction, Operation).

To make this bitemporal while keeping the granularity at the datom level, we need to introduce explicit bounds for the Valid Time. The System Time is still neatly handled by the Transaction entity (and retractions via the Operation flag).

Our expanded Bitemporal Datom becomes a 7-tuple: (E, A, V, T, Op, Valid_From, Valid_To)

E (Entity ID): A u64 identifier.

A (Attribute ID): A u32 or u64 mapping to schema definitions.

V (Value): The actual data (this is the trickiest part in a columnar model, which we'll address below).

T (Transaction ID): A u64 representing the System Time start. (A retraction datom with Op = false at a later T implies the System Time end).

Op (Operation): A bool (true for asserting a fact, false for retracting it).

Valid_From: A timestamp (e.g., i64 microseconds) representing when the fact became true in the domain.

Valid_To: A timestamp representing when the fact ceased to be true (often defaulting to infinity/MAX_INT).

2. In-Memory Engine: Apache Arrow
Apache Arrow is strictly columnar. Instead of storing an array of structs (our 7-tuple), we will store a struct of arrays (an Arrow RecordBatch).

A chunk of our database in memory will look like this:

Array	Arrow Data Type	Description
Entities	UInt64Array	The subject of the fact.
Attributes	UInt32Array	The property being defined.
Values	Polymorphic	The object of the fact.
Transactions	UInt64Array	Ties the datom to system time/metadata.
Operations	BooleanArray	true for add, false for retract.
Valid_From	TimestampArray	Domain time start.
Valid_To	TimestampArray	Domain time end.
The Polymorphic Value Challenge:
In Datomic, V can be a string, integer, boolean, ref, etc. Arrow prefers homogeneous columns. We have two realistic choices in Rust:

Arrow DenseUnionArray: We can create a union column that interleaves different types. This is flexible but can slightly degrade vectorized processing performance.

Type-Segregated Tables: We partition our datoms by value type. We have one RecordBatch for all String datoms, another for all Int64 datoms, another for Ref (Entity-to-Entity) datoms. This is exceptionally fast for columnar scanning.

3. On-Disk Persistence: Apache Parquet
Because Arrow and Parquet share the same columnar philosophy, writing an Arrow RecordBatch to a Parquet file using the parquet crate in Rust is highly optimized.

Our storage architecture would be an Append-Only LSM-Tree (Log-Structured Merge-tree) variant:

MemTable: Incoming transactions are batched in memory as Arrow RecordBatches.

Flushing: When the MemTable hits a size threshold, it is written immutably to disk as a Parquet file.

Indexing via Sorting: Datomic relies on covering indexes (trees sorted by EAVT, AEVT, AVET, VAET). In our columnar world, we achieve this by sorting our Arrow arrays before flushing to Parquet. For example, we might flush one Parquet file sorted by (E, A, Valid_From, T) and another sorted by (A, E, Valid_From, T).

Compaction: A background Rust thread reads smaller Parquet files, merges them, resolves overlapping Valid_To ranges or system time retractions if we want to prune history (though usually, we keep it all), and writes out larger, fully sorted Parquet files.

4. Querying the Model
With Parquet's metadata and row-group statistics, a query engine (potentially using Apache DataFusion, which is written in Rust and native to Arrow) can aggressively skip reading data from disk. If you are looking for an entity E = 123 at a specific Valid_Time, the engine only reads the specific Parquet files and row groups that contain that E and time range, bringing only the necessary columns into memory.

This gives us a highly compressed, vectorized, time-traveling data store. To move into the actual Rust implementation, we need to make a foundational design decision regarding how we structure the columnar data.

1. The Core Implication: Strict Attribute Schemas

In a purely weakly-typed system, you could assert [123, :age, "twenty", ...]. 2. The Typed MemTable Architecture
In Rust, using the arrow crate, we won't define a single "Database" table. Instead, we will define a struct that holds multiple, type-specific "Partition Builders."

To start, let's define the most common primitives we'd need:

Ref: A u64 pointing to another Entity (this makes our graph).

Int64: Standard integers.

String: UTF-8 text.

Boolean: True/False flags.

Float64: Decimals/floats.

Each of these will have its own dedicated Arrow builder in memory.

4. The Write Path (Routing)
When a transaction enters the system, it will look roughly like this:

Transaction Start: We assign a new T (System Time ID).

Iterate Datoms: For each datom in the transaction request:

Look up the Attribute A in our schema registry.

Determine its data type (e.g., String).

Acquire the mutable lock on the string_partition.

Push E, A, V, T, Op, Valid_From, and Valid_To into the respective array builders inside that partition.

Commit: Once all datoms are buffered into their builders, the transaction is marked successful.

When a TypedPartition hits a certain capacity (e.g., 1 million rows or a certain memory size), we call .finish() on its builders. This generates a purely immutable Arrow RecordBatch, which we immediately hand off to a background thread to serialize into a Parquet file on disk.

To make this routing work efficiently, we need to manage our Attribute Definitions (the schema). In Datomic, attributes are just entities themselves, defined by system-level datoms.

Should we bootstrap the schema by storing attribute definitions as Ref and String datoms inside the database itself (the elegant, self-hosting way), or should we maintain a separate, hardcoded metadata catalog to keep the query engine simpler during this initial build?

Which approach would yield the highest speed/throughput?

If raw speed and maximum throughput are our absolute north stars, a separate, dedicated in-memory metadata catalog is hands down the winner. While the "self-hosting" Datomic approach is mathematically and philosophically beautiful, it introduces significant friction in the hottest part of our database: the ingestion loop.

Here is exactly why the separate catalog wins for speed, and how we should engineer it.

1. The Write-Path Hot Loop
During a bulk insert, we might be throwing millions of datoms per second at the database. For every single datom, the ingestion engine must ask: "What type is attribute A?" so it knows which typed MemTable to route the data to.

If the schema is in the DB: Even if we cache it, we are fundamentally treating schema data as EAVT data. That means navigating database abstractions, potentially dealing with transaction isolation logic, and fighting cache invalidation just to figure out a data type.

If the schema is a separate in-memory catalog: We can use a highly optimized data structure. If our Attribute IDs (A) are strictly sequential (e.g., 1, 2, 3...), our schema registry is just a Rust Vec<DataType>. Checking an attribute's type becomes a direct array indexing operation (schema[a]). That takes less than a nanosecond. If the IDs are sparse, a fast-hashing map like FxHashMap or AHash is still practically instantaneous.

2. The Read-Path Query Planning
When an application queries the database, the query planner needs to know the types to generate the correct vectorized execution plan for Apache Arrow/DataFusion. A dedicated metadata catalog allows the query planner to instantly resolve all types and pinpoint exactly which Parquet files to scan, without having to execute a "pre-query" against the database just to understand the schema.

3. The "Best of Both Worlds" Architecture
We don't have to abandon the elegance of a self-hosted schema forever; we just separate the storage from the runtime execution.

For our initial build, we should hardcode or load a simple JSON/YAML file into a fast Rust HashMap on startup.
Later, if we want the DB to store its own schema, we use an RCU (Read-Copy-Update) pattern:

The database stores schema definitions as normal EAVT datoms.

On startup, the database queries itself for these datoms and constructs a highly optimized, read-only memory structure (like an Arc<Vec<DataType>>).

The ingestion hot-loop and query planner use this Arc reference. They never query the DB for schema types. They just read the memory structure instantly.

If a user alters the schema, we rebuild the memory structure in the background and atomically swap the Arc pointer.

This keeps the EAVT storage elegant but guarantees zero-cost abstractions on the critical speed paths.

Side quest: Is Apache DataFusion capable of being extended to implement a Datomic-style Datalog implementation in Rust?

That is a brilliant side quest, and the short answer is yes, absolutely. In fact, building a custom query language on top of DataFusion is one of its primary use cases. People often mistake DataFusion for just a "SQL database," but it is actually a decoupled, extensible query execution framework. The SQL parser is completely optional.

Because Datalog is fundamentally just declarative logic programming that maps beautifully to relational algebra (joins, filters, and projections), DataFusion's high-speed engine is a perfect backend for it.

Here is how you would map a Datomic-style Datalog implementation into DataFusion's Rust ecosystem:

1. The Parser: Bypassing SQL entirely
You would completely ignore DataFusion's default sqlparser-rs integration. Instead, you would write a custom parser using a Rust parser-combinator library like nom, pest, or logos.

Your parser's job is to take a Datalog query string like:
[:find ?name :where [?e :user/age 25] [?e :user/name ?name]]
and turn it into a custom Rust Abstract Syntax Tree (AST).

2. The Logical Plan: Translating Datalog to Relational Algebra
This is where the magic happens. DataFusion provides a programmatic LogicalPlanBuilder API. You would write a query planner that walks your Datalog AST and translates it into DataFusion logical operators:

:where clauses (Data Fetching): Each individual pattern like [?e :user/age 25] translates into a TableScan (hitting our Int64 MemTable/Parquet file for the :user/age attribute) combined with a Filter (where value == 25).

Unification (Variables): In Datalog, repeated variables represent joins. Because ?e appears in both [?e :user/age 25] and [?e :user/name ?name], your planner would instruct DataFusion to construct an InnerJoin between the two table scans on the Entity column.

:find clauses (Projection): The requested output variables (?name) translate directly into a DataFusion Projection node, ensuring only the needed columns are yielded to the user.

3. The Execution Phase
Once you hand DataFusion the LogicalPlan you constructed, it takes over. It applies its own physical optimizations (predicate pushdown, vectorization, choosing hash-joins vs. sort-merge joins based on your typed MemTables) and executes the query at near-bare-metal speeds using Apache Arrow arrays.

The "Final Boss": Recursive Rules
The only major hurdle you will face is Datalog's support for recursive rules (where a rule depends on itself, typically evaluated using a "fixpoint" algorithm).
Standard DataFusion is optimized for one-pass relational algebra (though it has some support for recursive CTEs). To implement true, unbound Datalog recursion, you would likely need to leverage DataFusion's extensibility to write a custom ExecutionPlan node. This custom Rust node would loop over a SendableRecordBatchStream, repeatedly joining new inferred facts against known facts until no new rows are produced (the fixpoint).

Using DataFusion to execute Datalog gives you the expressive, graph-like querying power of Datomic but with the columnar, SIMD-accelerated throughput of a modern OLAP engine.

1. The Bitemporal Context (XTDB Style)

The Translation: When the parser hits a predicate, it translates it into a standard DataFusion scalar function applied to the Arrow arrays. This means your math and string manipulations will be fully vectorized and SIMD-accelerated.

3. Implicit Joins & Unification

The Implementation: DataFusion is built for relational joins.

The Translation: We translate shared variables into standard InnerJoin nodes on the Entity column. Since our MemTables are already strongly typed and partitioned, these joins will be extremely efficient memory-to-memory operations.

4. The Boss Fight: Recursive Rules
This is where we have to build the custom bridge. Datalog engines like Datascript and Datomic support recursive rules (where a rule calls itself, like finding a path through a graph of unknown depth). Standard relational algebra doesn't do unbound recursion natively.

To achieve this, we cannot just use DataFusion's built-in operators. We have to write a custom physical operator in Rust:

Custom ExecutionPlan: We will implement DataFusion's ExecutionPlan trait to create a custom DatalogRuleExec node.

Semi-Naive Evaluation: Inside this Rust node, we will implement the "Semi-Naive Evaluation" algorithm. This is the standard way to evaluate recursive Datalog. It works by looping: it takes newly discovered facts (the delta), applies the rule to them to find more new facts, and repeats this until an iteration produces zero new facts (reaching the "fixpoint").

Arrow Native: Because we are writing this operator in Rust using the arrow crate, even this recursive loop will process data in batches of columnar arrays, keeping it highly performant.

By building this custom recursive operator and leveraging DataFusion for the heavy lifting of filters, joins, and aggregations, we get the exact semantics of XTDB/Datomic with the execution speed of a modern OLAP engine.

This is the exact right question to ask. In database engineering, the ingestion architecture dictates the absolute limits of your system.

Before giving the numbers, we have to establish one critical reality about Apache Arrow: Arrow array builders (Int64Builder, StringBuilder, etc.) are fundamentally not thread-safe. They are heavily optimized to allocate contiguous blocks of raw memory.

Because of this, a concurrent approach isn't just about adding locks; it dictates how we manage memory. Let's break down the tradeoffs between the two approaches.

Approach A: The Single Dedicated Writer (The Actor/Channel Pattern)
In this model, all incoming transactions are pushed onto a lock-free queue (like Rust's crossbeam::channel). A single background thread continuously pops transactions off this queue and exclusively mutates the MemTable builders.

Implementation Complexity: Low. You completely eliminate data races, lock contention, and deadlocks on the write path. The writer thread has exclusive &mut access to the builders.

Write Throughput: 100% (Our Baseline).
Do not underestimate single-core performance in Rust. Without the overhead of acquiring and releasing locks (which forces CPU cache invalidations), a single tight loop writing to Arrow arrays can easily ingest 100,000 to 500,000 datoms per second on a modern CPU. The CPU cache stays hot, and branch prediction works perfectly.

Read Throughput: ~95% to 100% of maximum possible.
Because the writer is single-threaded, we can use an RCU (Read-Copy-Update) or Double-Buffering pattern for reads. When a query comes in, it grabs an atomic reference counter (Arc) to an immutable snapshot of the MemTable. The query does no locking. It just reads.

Approach B: Multi-threaded Concurrent Writers
To achieve concurrent writes given Arrow's lack of thread safety, we cannot just wrap the MemTable in a Mutex (that would actually make it slower than Approach A due to lock contention).

Instead, we have to use Thread-Local MemTables. If we have 8 worker threads handling API requests, each thread has its own private MemTable.

Implementation Complexity: Very High.
We now have to manage multiple disjoint MemTables. To issue a globally correct Transaction ID (T) across threads, we need atomic counters. More importantly, when it's time to flush to disk, we have to coordinate merging 8 different MemTables, sorting them, and ensuring bitemporal rules (like resolving retractions) are handled correctly across parallel chunks of time.

Write Throughput: ~300% to 500%+ (Highly Scalable).
If your workload requires ingesting millions of datoms per second (e.g., massive IoT firehoses or bulk-loading entire historical datasets), this is the only way to scale out across CPU cores. The throughput scales roughly linearly with your core count, minus the overhead of the eventual merge phase.

Read Throughput: ~70% to 80% (Moderate Penalty).
Reads become significantly more complex. When a query executes against the in-memory data, the query engine now has to scan all 8 thread-local MemTables simultaneously, merge-sort the results on the fly, and resolve temporal overlaps dynamically before even hitting the disk. This scattered memory access slows down vectorized execution.

The Tradeoff Summary
Metric	Single Writer (Channel)	Multi-threaded (Thread-Local)
Write Speed	Baseline (Extremely fast, but bounded by 1 core)	Up to 5x+ higher (Scales with cores)
Read Speed	Maximized (Contiguous, lock-free snapshots)	Slower (Requires scatter-gather merging)
Complexity	Simple, elegant, predictable	Complex synchronization and merge phases
Ideal Use Case	OLTP, standard web apps, heavy read/analytics	Massive bulk ingestion, high-frequency firehoses

Let's break down exactly how we guarantee indefinite read scalability, build an aggressively optimized WAL, and achieve strict ACID semantics in Rust.

1. Indefinite Read Scalability (Separation of Storage & Compute)
Because our data model is bitemporal and append-only, our data is fundamentally immutable. Once a Parquet file is written, it never changes. Once a transaction is logged, it is never mutated.

This makes scaling read throughput trivial:

The Query Nodes (Peers): You can spin up 10, 100, or 1,000 independent Query Nodes. They do not need to coordinate with each other.

The Cache: Each Query Node pulls Parquet files from shared storage (like S3, a distributed file system, or replicated local disks) into its own local memory or SSD cache.

The Sync: The only thing the Query Nodes need from the Transactor is a tiny broadcast heartbeat: "I just committed Transaction 10,452." * Result: A Query Node handles complex recursive Datalog queries entirely using its local CPU and cached Arrow arrays. Reads never block writes, and writes never block reads. You get infinite, lock-free read scalability.

2. The "Insanely Performant" WAL
To get durability without bottlenecking our ingestion speed, our Write-Ahead Log must be mechanical sympathy in software form. fsync (forcing data to physical disk) is the enemy of throughput. We will beat it using two techniques:

Zero-Copy Serialization (rkyv): Instead of serializing incoming transactions to JSON or even standard Protocol Buffers, we will use a Rust crate like rkyv. It allows us to take the raw memory layout of our Rust transaction structs and blast them directly to disk. When reading from the WAL during crash recovery, rkyv validates the bytes and casts the pointer. Zero allocation, zero deserialization cost.

Group Commit (The Throughput Engine): If 10,000 users submit a transaction in the same millisecond, we do not call fsync 10,000 times. The Transactor places incoming transactions into a highly optimized ring buffer. A dedicated disk-I/O thread drains this buffer, batches all 10,000 transactions into a single contiguous block, writes it to the WAL file, and calls fsync exactly once. It then notifies all 10,000 waiting clients that their data is safe. This turns random concurrent writes into pure sequential I/O, maximizing disk bandwidth.

3. ACID Semantics in a Bitemporal World
Even though we are deferring the heavy lifting of sorting and flushing Parquet files to background threads, we still provide ironclad guarantees:

Atomicity: A transaction is a single entry in the WAL. If the system crashes halfway through writing the entry, the checksum fails on reboot, and the torn transaction is ignored. All datoms in a transaction succeed, or none do.

Consistency: The Transactor strictly validates schema types and business rules (if any) in memory before writing to the WAL.

Isolation (Strict Snapshot Isolation): Because every fact has a System Time (T), Multi-Version Concurrency Control (MVCC) is built into the fabric of our data. When a Query Node executes a query, it binds it to a specific T. Even if the Transactor is rapidly adding new data, the Query Node ignores anything newer than its T. There are no dirty reads or phantom reads.

Durability: A transaction is strictly kept in the Transactor's memory and is not acknowledged as "successful" to the client until the WAL's fsync hardware interrupt returns. If the server loses power 1 millisecond later, the Parquet files might not be updated, but on reboot, the database will replay the WAL into the MemTables. No data is lost.

How would you like clients to submit data to the database: as raw Datomic-style arrays [[:db/add 123 :name "Alice"]], or as nested JSON/EDN maps {:db/id 123, :name "Alice"} that the server flattens into datoms?

What performance costs do we incur if we support both? That is, both of those are valid EDN, the latter being more human readable.

Supporting both raw arrays and nested maps is standard practice in the Datomic/XTDB ecosystem because it provides a vastly superior developer experience.

The good news is that the theoretical performance cost to the storage engine is zero. The database fundamentally only stores flat datoms.

The real cost is CPU time and memory allocation during ingestion, specifically the overhead of parsing EDN and "flattening" nested maps. If we aren't careful, this step will severely bottleneck our single-threaded Transactor.

Here is a breakdown of the specific performance costs and how we architect our way around them.

1. The "EDN Tax" (Parsing & Allocation)
Raw arrays ([:db/add 123 :name "Alice"]) map almost 1:1 to our bitemporal (E, A, V, Op) tuple. They require minimal processing.

Nested maps ({:db/id -1, :name "Alice", :address {:db/id -2, :city "Oaxaca"}}) require graph traversal and flattening. To process this map, the system must allocate new memory to unroll it into three distinct datoms:

[-1 :name "Alice"]

[-2 :city "Oaxaca"]

[-1 :address -2]

If our single Transactor thread has to parse strings, traverse maps, and dynamically allocate vectors to flatten this data, our ingestion throughput will plummet from hundreds of thousands of operations per second down to the tens of thousands.

2. Temporary ID Resolution
Notice the -1 and -2 above. When users submit nested maps for new entities, they use temporary IDs (often negative integers or strings). The Block Allocation Strategy
We shift the responsibility of ID generation to the API worker nodes, but we keep the Transactor as the ultimate source of truth.

Pre-fetching: When an API worker thread boots up, it makes a tiny, asynchronous request to the Transactor: "Give me a block of IDs."

The High-Water Mark: The Transactor maintains a single atomic u64 (the high-water mark). It increments it by 10,000, and replies to the API worker: "You own IDs 1,000,000 through 1,009,999." (This takes the Transactor nanoseconds).

Local Resolution: A user submits an EDN payload with temporary IDs to the API worker:
[{:db/id -1, :name "Alice", :friends [-2]}, {:db/id -2, :name "Bob"}]

Flattening: The API worker uses its local, pre-fetched block to assign permanent IDs. It maps -1 to 1,000,000 and -2 to 1,000,001. It flattens the maps into tuples and resolves all references internally.

The Handoff: The API worker serializes the fully resolved, flat datoms and sends them to the Transactor's queue.

The Response: The API worker immediately responds to the user with the translation map ({-1: 1000000, -2: 1000001}), while the Transactor blindly and blazingly fast appends the data to the MemTables and the WAL.

If an API worker crashes, we might "lose" a few thousand unused IDs from its block. In a u64 space, a few thousand skipped numbers are mathematically irrelevant. We will run out of atoms in the universe before we run out of u64 IDs.

1. The Disk Space Reality (The Parquet Compression Magic)
If you logically duplicate your data four times, you might expect a 400% increase in disk space. In a row-based database (like PostgreSQL), this is exactly what happens. But in a columnar format like Apache Parquet, the math is entirely different.

Parquet compresses data per column using algorithms like Run-Length Encoding (RLE) and Dictionary Encoding.

AEVT Index Example: In an AEVT-sorted Parquet file, the Attribute (A) column is grouped together. If you have 10,000 datoms for the :user/age attribute, the A column looks like [:user/age, :user/age, :user/age...] 10,000 times. Parquet's RLE simply stores [Value: :user/age, Count: 10,000]. That entire column shrinks to a few bytes.

The Reality: Because sorting drastically increases consecutive identical values in columnar data, compression ratios skyrocket. A 4x logical duplication in Parquet usually results in only a 1.5x to 2.5x increase in actual disk footprint compared to storing a single unindexed, uncompressed dataset.

Given how cheap NVMe storage is today, paying a 2x storage penalty to achieve O(1) query planning and sequential read speeds is the best trade you can make.

2. The Compaction Performance Penalty (Write Amplification)
While storage is cheap, CPU and Disk I/O bandwidth are not. Generating all four indexes means that when your background Compactors wake up to process a 64MB MemTable flush, they must:

Sort the data four distinct ways in RAM.

Compress the data four distinct ways.

Write four distinct Parquet files to disk.

The Penalty: You are paying a 4x Write Amplification penalty during background compaction. If your ingestion rate is extremely high, your background threads might saturate the disk's write bandwidth trying to write out all four indexes, causing the compaction queue to back up.

The Solution: We don't block the Transactor, but we do need robust thread-pool sizing. We can easily afford this penalty on a multi-core machine because sorting Arrow arrays using Rust's slice::sort_unstable_by (or DataFusion's highly optimized sort kernels) is incredibly fast. We just dedicate 4-8 background cores purely to index generation.

No, we do not need distinct, time-first indexes (like ValidFrom_E_A_V). This is where Parquet's metadata features save us from combinatorial explosion.

Instead of making time the primary sort key, we append our bitemporal fields to the end of our core indexes. Our physical sorting looks like this:

EAVT: (Entity, Attribute, Value, Valid_From, Valid_To, System_T)

AEVT: (Attribute, Entity, Value, Valid_From, Valid_To, System_T)

AVET: (Attribute, Value, Entity, Valid_From, Valid_To, System_T)

VAET: (Value, Attribute, Entity, Valid_From, Valid_To, System_T)

How queries use this without a time index:
Parquet files are broken into "Row Groups" (e.g., chunks of 1 million rows). For every single column in a Row Group, Parquet stores Min/Max Statistics (also known as Zone Maps) in the file footer.

If a user executes a query looking for Alice’s :user/age as it was in the year 2023, the query engine (DataFusion) does the following:

It quickly binary-searches the file footers to find the Row Groups containing A = :user/age and E = Alice.

Before it actually reads the data from disk into RAM, it checks the Min/Max stats for the Valid_From column in that Row Group.

If the Max(Valid_From) in that chunk is from 2022, DataFusion completely ignores that Row Group. It reads nothing from disk.

2. Solving Write Amplification: Staged Index Generation
If Cores 3 and 4 try to generate EAVT, AEVT, AVET, and VAET all at once every time a MemTable flushes, they will peg the CPU at 100% and saturate the disk I/O, causing the OS to choke on Core 1 and 2's operations.

Instead, we borrow from classic LSM-tree design and stagger the work based on query necessity:

Level 0 (The Flush): When the MemTable fills up, Cores 3/4 write a single Parquet file sorted by Time and Entity (T, E). This is extremely fast because the data is naturally ordered by Time arriving at the Transactor. Disk I/O impact: Minimal.

Level 1 (The Primary Indexes): When Level 0 files accumulate, Cores 3/4 merge them into EAVT and AEVT Parquet files. These are the two most critical indexes for 90% of Datalog queries (Entity lookups and Attribute scans).

Level 2 (The Heavy Indexes): Only when the system detects low I/O pressure (or on a delayed schedule), it reads the Level 1 files and generates the AVET (Value search/Filtering) and VAET (Reverse graph traversal) indexes.

The User Experience Impact: If a user runs a reverse-graph query (VAET) immediately after inserting data, DataFusion still answers it correctly. It just has to use the in-memory MemTable or do a slightly slower hash-filter on the EAVT files until the true VAET index is built a few minutes later.

3. Memory vs. Compaction Frequency (The Tuning Dial)
We need to balance how long data stays in memory (which slows down reads) versus how often we flush to disk (which increases write amplification).

The "Micro-Batch" Problem: If we flush every 1 second (e.g., 10MB chunks), memory usage is tiny, but Cores 3 and 4 will be constantly creating thousands of tiny Parquet files. DataFusion will struggle to read 1,000 tiny files, and disk metadata overhead will skyrocket.

The "Mega-Batch" Problem: If we flush every 5 minutes (e.g., 2GB chunks), disk I/O is highly optimized. But the MemTable grows massive. Every time Core 2 executes a read query, it has to scan a 2GB unindexed memory buffer and resolve millions of bitemporal overlaps on the fly. Read latency will spike noticeably.

The Solution: Adaptive Backpressure
We don't use a hardcoded timer. We use memory and I/O thresholds.

The MemTable flushes only when it hits a "Goldilocks" size for Parquet Row Groups (e.g., 64MB to 128MB). On a busy system, this might be every 5 seconds. On a quiet system, it might be every 2 hours.

If the Transactor is ingesting data so violently that the MemTable hits 500MB before Cores 3/4 can finish their Level 0 flush, the database initiates Backpressure. The Transactor artificially slows down its acknowledgment to API workers (e.g., adding a 5ms delay) to let the background I/O catch its breath.

This guarantees the database never runs out of memory and never completely locks up, smoothly degrading write throughput only when the physical limits of the SSD are reached.

By staggering the index generation and tuning the MemTable size to Parquet's sweet spot (~64MB), a 4-core/16GB machine can comfortably handle thousands of inserts per second while maintaining highly responsive Datalog queries.

Querying (The Read Path): When a user writes a Datalog query like [:find ?e ?score :where [(fulltext $ :post/body "MesoDB rules") [[?e ?score]]]], our query planner intercepts the fulltext call. It asks Tantivy to execute the search, which returns an array of matching Entity IDs and their TF-IDF/BM25 scores. We instantly convert this into an Apache Arrow RecordBatch and hand it to DataFusion to InnerJoin against the rest of the bitemporal graph data.

The user gets a seamless Datalog experience, and we maintain our separation of storage and compute.

The MesoDB Cargo Workspace

A lightweight command-line tool (built with clap) that connects to mesodb-server or instantiates mesodb-core directly for local debugging and REPL interactions.

The Wire Protocol: Apache Arrow Flight
You mentioned wanting a "very thin, high-performance wire protocol." Since our entire in-memory representation is Apache Arrow, we get to use an incredible piece of technology: Arrow Flight.

Arrow Flight is an RPC framework (built on top of gRPC) specifically designed for streaming columnar Arrow data over the network.

Standard gRPC/JSON: You query the database -> the DB serializes the data to JSON/Protobuf -> sends it over the wire -> the client deserializes it back into memory. (Huge CPU penalty).

Arrow Flight: You query MesoDB -> DataFusion produces an Arrow RecordBatch in RAM -> Flight sends the exact binary layout over the TCP socket -> the client receives it and drops the pointer into memory. Zero-copy, zero-deserialization over the network.

If a Python client queries the mesodb-server over Arrow Flight, the data lands directly into a Pandas or Polars dataframe instantaneously.

The Impedance Mismatch
The core technologies we have chosen—Apache DataFusion (for queries) and Tokio (for our background compaction and WAL threads)—are deeply, fundamentally asynchronous.

DataFusion uses async rust to read Parquet files concurrently, stream Arrow batches, and execute query plans across multiple cores. If we try to write MesoDB's internal core as purely synchronous, we will constantly be fighting DataFusion, forcing blocking calls where the library expects to yield, and potentially causing thread deadlocks.

The "Rust Way" to Provide Both APIs
We solve this by building the internal engine entirely in async, and then wrapping it to provide a sync API.

1. The Internal Core (Async by Default)
Everything inside mesodb-core is written as async fn.

Rust
// Internal async implementation
impl MesoDb {
    pub async fn transact(&self, tx_data: Vec<Datom>) -> Result<TxReport> { ... }
    pub async fn query(&self, datalog: &str) -> Result<RecordBatch> { ... }
}
2. The Async API (Direct Expose)
For users writing high-performance web servers (like Axum or Actix), they use the async API directly with zero overhead.

Rust
// User code

let results = db.query("[:find ?e ...]").await?;
3. The Sync API (The blocking Module)
To provide the synchronous SQLite-like experience, we create a sub-module (e.g., mesodb::blocking). Inside this module, we instantiate a hidden, lightweight Tokio runtime. When a user calls the sync API, we just pass the call into the async core and block the thread until it finishes.

Rust
// Inside mesodb-core/src/blocking.rs
pub struct BlockingDb {
    inner: MesoDb,
    rt: tokio::runtime::Runtime,
}

impl BlockingDb {
    // This is a standard, synchronous function
    pub fn transact(&self, tx_data: Vec<Datom>) -> Result<TxReport> {
        // We block the current thread while the async core does the work
        self.rt.block_on(self.inner.transact(tx_data))
    }
}
The Tradeoffs of Having Both
Pros: Maximum reach. Data scientists using Python FFI or developers writing simple CLI tools can use the blocking API without pulling in Tokio or understanding Rust futures. High-performance web servers can use the async API to handle 100,000 concurrent connections.

Cons: Code duplication. You essentially have to write the public-facing function signatures twice (once for async, once for sync). This makes documentation a bit heavier. However, you can use Rust macros to generate the sync wrappers automatically to keep maintenance low.

By accepting async as the internal reality of our modern columnar stack, we can effortlessly provide a mesodb::blocking wrapper that gives users the exact SQLite-style synchronous experience you are aiming for.

Here is why pest hits the absolute sweet spot for MesoDB, and why the other options either overcomplicate things or optimize the wrong bottleneck.

1. Why Not tree-sitter or nom?
tree-sitter is Overkill: It is a phenomenal tool, but it is designed for incremental parsing in IDEs (parsing code as a user types it, character by character). It also relies on C bindings, which pollutes our pure-Rust mesodb-core library and complicates cross-compiling.

nom is the "Macro Soup" Trap: nom is the fastest byte-level parser in the Rust ecosystem. If we were parsing a binary network protocol, I would choose nom instantly. But Datalog queries are deeply nested, human-readable strings (essentially Clojure's EDN format). Writing a parser for nested arrays, maps, and bitemporal logic in nom results in highly complex, deeply nested Rust combinator code that is notoriously difficult to read, debug, and modify.

2. The pest Sweet Spot
pest uses Parsing Expression Grammars (PEG). It allows you to define your entire Datalog language syntax in a single, perfectly readable .pest file, and then it automatically generates high-performance Rust code via a macro at compile time.

Here is why it aligns perfectly with our goals:

Simplicity and Readability: If we want to add a new bitemporal keyword to our Datalog dialect later (e.g., :as-of), we don't have to rewrite complex Rust logic. We just add one line to the .pest file.

The "Fast Enough" Reality Check: Parsing a 200-byte Datalog query string using pest takes microseconds. The DataFusion query planning, disk I/O, and join execution will take milliseconds. The parser is never going to be the bottleneck in MesoDB's read path. Sacrificing a few nanoseconds of parser speed for massive gains in maintainability is a trade we should make every time.

World-Class Error Messages: When a user inevitably typos their Datalog query (e.g., missing a closing bracket ]), pest makes it incredibly easy to generate beautiful, compiler-like error messages pointing to the exact line and character of the syntax error. This is a huge win for UX.

3. What the Implementation Looks Like
With pest, our implementation becomes wonderfully decoupled.

We create a datalog.pest file that reads almost like plain English rules. For example, to parse a Datalog variable (like ?name) or a keyword (like :user/age):

Rust
// datalog.pest
WHITESPACE = _{ " " | "\t" | "\r" | "\n" }

variable = @{ "?" ~ ASCII_ALPHANUMERIC+ }
keyword  = @{ ":" ~ (ASCII_ALPHANUMERIC | "/" | "-" | "_")+ }
string   = ${ "\"" ~ inner_string ~ "\"" }
number   = @{ "-"? ~ ASCII_DIGIT+ }

// A data pattern like: [?e :user/age 25]
pattern  = { "[" ~ variable ~ keyword ~ (variable | string | number) ~ "]" }

1. Traditional Datomic-Style Syntax
In a standard Datomic (or Datascript) model, temporal concepts are usually handled outside the query syntax. You get a snapshot of the database at a specific time (db.as_of(t)), and then you pass that snapshot into the query function. The Datalog syntax itself remains blissfully ignorant of time.

The Query: "Find the names and emails of all users older than 18."

Clojure
[:find ?name ?email
 :where
 [?e :user/age ?age]
 [(>= ?age 18)]
 [?e :user/name ?name]
 [?e :user/email ?email]]

2. Custom MesoDB Bitemporal Syntax
To unleash the full power of a bitemporal engine directly within the query language, we can extend the Datalog grammar. We can add specific top-level keywords for System Time (when the data was recorded) and Valid Time (when the fact was true in the real world).

The Query: "Find the names and emails of users who were older than 18, as the database knew it at transaction 10,452, but specifically looking at what was valid in the real world on January 1st, 2023."

Clojure
[:find ?name ?email
 :as-of-tx 10452                         ;; System Time bound
 :as-of-valid #inst "2023-01-01T00:00:00Z" ;; Valid Time bound
 :where
 [?e :user/age ?age]
 [(>= ?age 18)]
 [?e :user/name ?name]
 [?e :user/email ?email]]

We could also extend the [:where] patterns themselves to let users project the bitemporal boundaries of a fact directly into variables. This allows users to query the history of an entity over time.

The Query: "Find all the past names of Entity 123, and exactly when those names were valid in the real world."

Clojure
[:find ?old_name ?start ?end
 :where
 ;; Extended tuple: [E A V ...Valid_From Valid_To]

Rust

pub struct Query {
    pub find: Vec<Variable>,

    // MesoDB custom bitemporal bounds
    pub as_of_tx: Option<u64>,
    pub as_of_valid: Option<DateTime>,

    pub where_clauses: Vec<WhereClause>,
}

pub enum WhereClause {
    // A standard [E A V] or extended [E A V Valid_From Valid_To] pattern
    Pattern {
        entity: Term,
        attribute: Term,
        value: Term,
        valid_from: Option<Variable>, // For the tuple-level time travel
        valid_to: Option<Variable>,
    },
    // A predicate like [(>= ?age 18)]
    Predicate(PredicateExpr),
}

pub enum Term {
    Variable(String),  // ?name
    Keyword(String),   // :user/name
    Literal(LiteralValue), // 18, "Alice"
}

2. The Datalog pull Engine (The Default)
The pull syntax is the crown jewel of graph databases. It allows front-end developers to request exactly the shape of the data they need (much like GraphQL) without writing massive, complex JOIN statements.

The Syntax:

Clojure
[:find (pull ?e [:user/username :user/email {:user/address [:address/city :address/zip]}])
 :where
 [?e :user/status "active"]]
How MesoDB executes this (The "Nesting Tax"):

DataFusion executes the :where clause at maximum columnar speed, resulting in a flat list of matching Entity IDs (?e).

MesoDB then takes those IDs and executes a recursive "Pull Execution" phase.

It does rapid index lookups (using the EAVT MemTable and Parquet indexes) for :user/username and :user/email.

It recursively follows the edge for :user/address to the next entity, grabbing its city and zip.

It allocates memory to construct a deeply nested JSON/EDN structure and serializes it to the client.

This takes CPU cycles and memory allocations, but it saves the developer from writing hundreds of lines of mapping code on the client side.

3. The Analytical Escape Hatch (Query Directives)
For a Python script loading 10 million rows into a Pandas DataFrame, that "Nesting Tax" is completely unacceptable. We bypass it using a top-level Directive.

The Syntax:

Clojure
[:find ?username ?email ?city ?zip
 :return :tabular  ;; <--- The Escape Hatch Directive
 :where
 [?e :user/status "active"]
 [?e :user/username ?username]
 [?e :user/email ?email]
 [?e :user/address ?addr]
 [?addr :address/city ?city]
 [?addr :address/zip ?zip]]
How MesoDB executes this (Zero-Copy):

DataFusion executes the joins and produces an Apache Arrow RecordBatch in RAM (a flat table of columns).

Because the directive is :tabular, MesoDB skips the entire JSON/EDN serialization phase.

If the client connects via Arrow Flight (our wire protocol), MesoDB literally streams the raw memory pointers over the TCP socket. Zero allocation. Zero parsing. The data arrives in Pandas instantaneously.

/// The main authentication middleware that wraps our API routes.
pub async fn auth_middleware(req: Request, next: Next) -> Result<Response, StatusCode> {
    // 1. Extract the Authorization header
    let auth_header = req.headers()
        .get(header::AUTHORIZATION)
        .and_then(|value| value.to_str().ok());

    match auth_header {
        Some(header_val) if header_val.starts_with("Basic ") => {
            // Day One: Handle Basic Auth
            let credentials = header_val.trim_start_matches("Basic ");
            if validate_basic_auth(credentials) {
                Ok(next.run(req).await)
            } else {
                Err(StatusCode::UNAUTHORIZED)
            }
        }
        Some(header_val) if header_val.starts_with("Bearer ") => {
            // Day Two: JWT Stub
            let token = header_val.trim_start_matches("Bearer ");
            if validate_jwt_stub(token) {
                Ok(next.run(req).await)
            } else {
                Err(StatusCode::UNAUTHORIZED)
            }
        }
        _ => {
            // No auth header, or unrecognized format
            Err(StatusCode::UNAUTHORIZED)
        }
    }
}

The Physics:

When Disabled (e.g., log level is INFO, but the code has debug!()): The performance impact is essentially a single atomic read and a predictable branch. It takes about 1 to 2 nanoseconds. It is effectively zero-cost.

When Enabled (e.g., logging every datom): Formatting a string, acquiring a lock on standard output, and flushing it to the console or a file takes thousands of nanoseconds (microseconds).

The Danger Zone:
If we put a trace!("Processing datom: {:?}", datom) inside the Transactor's inner for loop, and a developer sets RUST_LOG=trace, our ingestion throughput will drop from 500,000 datoms/second down to maybe 20,000 datoms/second. The database will become entirely bottlenecked by terminal I/O.

The Solution:
We keep tracing spans and logs at the batch and boundary level, never at the individual datom level.

We log when a transaction batch starts and completes.

We log when a MemTable flushes to Parquet.

We do not log the 10,000 individual tuples inside that transaction unless it's hidden behind a strictly warned #[cfg(debug_assertions)] block.

2. The Performance Impact of color-eyre
color-eyre provides beautiful, colorful error reports with full backtraces. It is a lifesaver for debugging.

The Physics:

The Cost of a Backtrace: To generate those beautiful errors, color-eyre must walk the execution stack of the CPU to capture the backtrace. This is computationally expensive, often taking tens to hundreds of microseconds.

Dynamic Allocation: eyre::Report uses dynamic dispatch (Box<dyn Error>), which requires heap allocation.

The Danger Zone:
If a user submits an EDN payload with a schema mismatch (e.g., sending a String to an Int64 attribute), and our API Worker returns an eyre::Result containing a backtrace, a user doing bulk inserts with dirty data will force the server to capture thousands of stack traces a second. The server's CPU will max out just generating error strings.

The "Fast Core, Rich Shell" Architecture
To get the best of both worlds, we separate our error handling into two distinct tiers. This is standard practice in high-performance Rust.

Tier 1: The Core Library (mesodb-core)
Inside the database engine, performance is king. We do not use color-eyre here. We use a standard, zero-allocation Rust enum via the thiserror crate.

Rust
// mesodb-core/src/error.rs
use thiserror::Error;

#[derive(Error, Debug)]
pub enum MesoError {
    #[error("Schema mismatch: Expected {expected}, got {found}")]
    SchemaMismatch { expected: String, found: String },

    #[error("Transaction conflict: Entity {0} failed unique constraint")]
    UniqueConstraintFailed(u64),

    #[error("I/O Error during WAL flush: {0}")]
    Io(#[from] std::io::Error),
}

// The core uses extremely fast, lightweight results.
pub type Result<T> = std::result::Result<T, MesoError>;
Why? When an API worker rejects a schema mismatch, it returns this enum. It takes zero heap allocation and zero backtrace generation. It is instantaneous.

Tier 2: The Binary Shell (mesodb-server & mesodb-cli)
This is where we introduce color-eyre. We wrap the fast core errors at the absolute edge of the system, right before they hit the developer's eyes.

Rust
// mesodb-server/src/main.rs
use color_eyre::eyre::Result;
use tracing::{info, error, instrument};

#[tokio::main]

    // 1. Initialize colorful errors and tracing subscriber
    color_eyre::install()?;
    tracing_subscriber::fmt()
        .with_env_filter(tracing_subscriber::EnvFilter::from_default_env())
        .init();

    info!("Starting MesoDB Server...");

    // ... setup axum server ...

    Ok(())
}

// In our HTTP handler:
#[instrument(skip(state, payload))] // Automatically logs timing and traces!
async fn handle_transact(...) -> impl IntoResponse {
    match state.db.transact(&payload).await {
        Ok(receipt) => Json(receipt).into_response(),
        Err(e) => {
            // We log the fast, lightweight MesoError.
            // If the user wants a full eyre report, they can configure it!
            error!("Transaction failed: {}", e);
            (StatusCode::BAD_REQUEST, e.to_string()).into_response()
        }
    }
}
The Verdict
By keeping the inner loops of mesodb-core strictly using lightweight enums (thiserror) and keeping tracing out of the per-datom iteration, we completely preserve our maximum throughput. By wrapping the binaries in color-eyre and tracing-subscriber, the developer running the server or CLI gets the gorgeous, filterable, backtrace-rich output they expect.

/// The permanent, unique identifier for an Entity in the graph.

pub type AttributeId = u32;

/// The System Time identifier (Transaction ID).

/// The strictly-typed Value variant for ingestion.
/// During ingestion, EDN/JSON maps to this Enum.
/// Later, this routes to the specific typed Arrow MemTable.
#[derive(Debug, Clone, PartialEq, PartialOrd)]
pub enum Value {
    Boolean(bool),
    Int64(i64),
    Float64(f64),
    String(String),
    /// A pointer to another EntityId. Crucial for graph traversals.
    Ref(EntityId),
    /// Temporal values
    Timestamp(TimestampMicros),
    /// A fixed 16-byte UUID for extremely fast scanning
    Uuid([u8; 16]),
}

impl fmt::Display for Value {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Value::Boolean(b) => write!(f, "{}", b),
            Value::Int64(i) => write!(f, "{}", i),
            Value::Float64(v) => write!(f, "{}", v),
            Value::String(s) => write!(f, "\"{}\"", s),
            Value::Ref(r) => write!(f, "Ref({})", r),
            Value::Timestamp(t) => write!(f, "Inst({})", t),
            Value::Uuid(u) => write!(f, "Uuid({:?})", u),
        }
    }
}
3. The Bitemporal Datom (src/datom.rs)
This is the atomic unit of MesoDB. Every fact in our universe is represented by this 7-tuple.

Rust
// src/datom.rs
use crate::types::{AttributeId, EntityId, TimestampMicros, TxId, Value};

/// The fundamental, immutable bitemporal fact in MesoDB.
#[derive(Debug, Clone, PartialEq)]
pub struct Datom {
    /// E: The subject of the fact
    pub e: EntityId,
    /// A: The property being defined
    pub a: AttributeId,
    /// V: The object/value of the fact
    pub v: Value,
    /// T: System Time (Transaction ID)
    pub t: TxId,
    /// Op: True for assertion (add), False for retraction (remove)
    pub op: bool,
    /// Valid From: When this fact became true in the domain
    pub valid_from: TimestampMicros,
    /// Valid To: When this fact ceased to be true (defaults to MAX)
    pub valid_to: TimestampMicros,
}

impl Datom {
    /// Creates a new assertion Datom with infinite valid_to.
    pub fn assert(
        e: EntityId,
        a: AttributeId,
        v: Value,
        t: TxId,
        valid_from: TimestampMicros,
    ) -> Self {
        Self {
            e,
            a,
            v,
            t,
            op: true,
            valid_from,
            valid_to: i64::MAX, // Infinity by default
        }
    }

    /// Creates a retraction Datom to end a fact's validity.
    pub fn retract(
        e: EntityId,
        a: AttributeId,
        v: Value,
        t: TxId,
        valid_from: TimestampMicros, // The exact time it stopped being true
    ) -> Self {
        Self {
            e,
            a,
            v,
            t,
            op: false,
            valid_from,
            valid_to: valid_from, // A retraction represents the boundary
        }
    }
}
